# Architectural Decisions

Meaningful architectural/technical decisions only. `PROJECT_SPEC.md` is the architecture
source of truth; this log records choices made while implementing it. Not a session diary.

## D-001 — pnpm workspace monorepo (S0, 2026-09-30)

- **Decision:** pnpm workspaces over `apps/*`, `packages/*`, `adapters/*`, per spec §44.
- **Reason:** Spec mandates a pnpm monorepo with logical capabilities as packages.
- **Alternatives:** npm/yarn workspaces, Nx/Turborepo — rejected as unnecessary tooling (§11, §50.4).

## D-002 — Source-only packages, no build step in S0 (S0, 2026-09-30)

- **Decision:** Packages export TypeScript source (`main`/`types` → `src/index.ts`) with `moduleResolution: Bundler`. Type checking is one root `tsc --noEmit` over all workspace sources; each package also has a `tsconfig.json` extending `tsconfig.base.json`.
- **Reason:** Simplest setup that is compile-safe and resolves workspace deps. Build/bundling is revisited when deployables need it (S9).
- **Alternatives:** TS project references with per-package builds — deferred, no S0 value.

## D-003 — Strict TypeScript (S0, 2026-09-30)

- **Decision:** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`.
- **Reason:** Deterministic lifecycle/verification code benefits from the strictest typing from the start.

## D-004 — Tooling: TypeScript 6.0, ESLint 9, Vitest, Prettier (S0, 2026-09-30)

- **Decision:** ESLint 9 flat config + typescript-eslint; Vitest; Prettier + `.editorconfig`. TypeScript pinned to `~6.0`.
- **Reason:** typescript-eslint 8.71 supports TypeScript `<6.1`; the newest TypeScript (7.0) caused an unmet-peer warning. Revisit when typescript-eslint supports TypeScript 7.

## D-005 — Next.js deferred to S7 — sequencing only (S0, 2026-09-30)

- **Decision:** `apps/web` is a plain TypeScript placeholder in S0.
- **Reason:** Avoids heavy React/Next dependencies with no S0 value. This is **sequencing only**: the locked architecture (spec §11.1) still requires `apps/web` to become a Next.js app, scheduled for S7.

## D-006 — `pnpm dev` fails loudly in S0 (S0, 2026-09-30)

- **Decision:** `pnpm dev` runs a script that prints "NOT IMPLEMENTED" and exits non-zero.
- **Reason:** Spec §39 expects `pnpm dev` to run web/api/worker/simulator; no runtime exists until S2+, so a success exit could be mistaken for a working local app.

## D-007 — `packages/contracts` limited to generic primitives in S0 (S0, 2026-09-30)

- **Decision:** Only a `Brand` helper, `IsoTimestamp`, and four ID aliases (organization, facility, asset, device). No S1 domain types.
- **Reason:** The domain model (cases, events, actions, verification, lifecycle) belongs to S1.

## D-008 — Documentation stubs only (S0, 2026-09-30)

- **Decision:** `ARCHITECTURE.md`, `DOMAIN_MODEL.md`, `THREAT_MODEL.md`, `AI_GOVERNANCE.md`, `EVIDENCE_STANDARD.md`, `HARDWARE.md` and `docs/submission/README.md` are phase-labelled stubs pointing to the spec.
- **Reason:** Spec §44 lists them; `PROJECT_SPEC.md` must remain the single architecture source of truth, so nothing is duplicated.

## D-009 — No Co-Authored-By trailer on commits (S0, 2026-09-30)

- **Decision:** Commits in this repository carry no `Co-Authored-By` line.
- **Reason:** Explicit project-owner instruction.

## D-010 — Domain contracts use plain string IDs; time is passed explicitly (S1, 2026-09-30)

- **Decision:** Domain types use `string` for IDs exactly as written in the spec (the S0 branded `OrganizationId` etc. remain available but are not required). Every command carries an explicit `at` timestamp; domain code never reads the system clock, environment or network, and does not yet depend on the `clock` package.
- **Reason:** Spec types use plain strings, and branding would make every fixture and later adapter verbose with no S1 benefit. Explicit time keeps transitions deterministic. A boundary test (`tests/unit/domain-boundaries.test.ts`) enforces purity.

## D-011 — Shared Result / DomainError / TransitionRecord live in `contracts` (S1, 2026-09-30)

- **Decision:** Domain operations return `Result<T, DomainError>`; transitions return `{ value, record }` where `record` is a `TransitionRecord`. `DomainError.code` distinguishes illegal lifecycle/action/recommendation transitions, missing verification reference, verification mismatch, invalid recurrence, missing active event and timestamp regression.
- **Reason:** Every domain package needs the same vocabulary; putting it in `contracts` avoids cross-domain dependencies. The record is what the audit package will persist later (spec section 37) without the domain doing I/O.

## D-012 — Package split and dependency direction (S1, 2026-09-30)

- **Decision:** `risk-cases` owns the case aggregate and its state machine; `risk-lifecycle` owns the RiskEvent state machine plus cross-aggregate coordinators (`completeVerification`, `reopenOnRecurrence`, `grantsMitigationCredit`); `recommendations` and `action-orchestration` own their models; `verification` holds only the assessment validator. Graph: contracts <- verification <- {recommendations, risk-cases} <- risk-lifecycle; action-orchestration -> contracts. No cycles (tested).
- **Reason:** Keeps illegal transitions unreachable through each aggregate's public API while letting cross-aggregate invariants live in one place. `verification` exposes synthetic fixtures through a `@symbiosis/verification/testing` subpath so tests share one assessment fixture.

## D-013 — Spec gaps resolved for S1 (S1, 2026-09-30)

- **Decision:** The spec names but does not define `TimeWindow`, `CriterionResult`, the RiskEvent shape, or transition tables beyond the happy path. S1 defines: minimal `TimeWindow` and `CriterionResult`; `RiskEvent` with `latestVerificationId`; transition tables in `CASE_TRANSITIONS`, `RISK_EVENT_TRANSITIONS`, `RECOMMENDATION_TRANSITIONS` and `ACTION_TRANSITIONS`. Notable choices: outcome states (`PARTIALLY_VERIFIED`, `NOT_IMPROVING`, `INCONCLUSIVE`) can re-enter `ACTION_REPORTED` for another cycle; `VERIFIED` events are terminal (recurrence creates a new event); recurrence can reopen only from `VERIFIED_IMPROVED` (corrected after S1: `CLOSED` is terminal and is never eligible, since closure does not imply a verified improvement existed; spec 4.1/8.3); a case cannot be closed while `VERIFYING`; `MitigationAction.reportedBy/reportedAt` are optional and present only once `REPORTED_COMPLETE` (spec lists them as required, which cannot hold for a merely assigned action); an action may be reported complete without prior acknowledgement.
- **Reason:** Required to implement the state machines without inventing replacement concepts. Revisit if later phases need different paths; changes must be recorded here.

## D-014 — VERIFIED requires a self-consistent assessment (S1, 2026-09-30)

- **Decision:** `validateVerificationAssessment` rejects a `VERIFIED` result unless there is at least one required criterion, all required criteria passed, and at least one evidence ID; it also checks ranges, windows and required fields. Lifecycle code accepts a verification outcome only through a valid assessment whose case/event match.
- **Reason:** Principle 3 / section 8.1: a verified state must be unforgeable by a bare status change. This is structural validation only; threshold evaluation, windows and policy execution remain S5.

## D-015 — Local edge API on `node:http`, transport-neutral handler (S2, 2026-09-30)

- **Decision:** `apps/api` exposes `createEdgeHandler(deps)`, a pure `(EdgeRequest) => EdgeResponse` function over raw body bytes, plus a thin `node:http` wrapper (`createEdgeServer`). No web framework was added.
- **Reason:** The signature covers the original bytes, so nothing may parse and re-serialize JSON first; `node:http` hands over the raw buffer with zero dependencies. Because the handler is transport-neutral, the Cloud Run deployment (S9) can reuse it unchanged. Bodies over 64 KiB get 413.
- **Alternatives:** Fastify/Express — rejected: extra dependency, body-parser hooks that risk altering raw bytes.

## D-016 — Edge signing format details left open by the spec (S2, 2026-09-30)

- **Decision:** The signed material is exactly the six spec lines joined by LF (no trailing newline). Choices the spec did not fix: `X-Timestamp` is Unix epoch seconds (decimal), `X-Seq` a non-negative decimal integer with no leading zeros, `X-Nonce` 16-64 chars of `[A-Za-z0-9_-]`, signature lowercase hex of HMAC-SHA256 (hex input accepted case-insensitively). PATH is the path alone; requests with a query string are rejected (400) because a query would be unsigned. Defaults: timestamps older than 300 s are stale, more than 60 s ahead are rejected. `firmware-contracts/sample-packets/signing-vector.json` is a known-answer vector computed independently (Python `hmac`) so firmware can reproduce it byte for byte.
- **Reason:** Epoch seconds avoid ISO formatting ambiguity on a microcontroller; canonical integer forms remove signing ambiguities.

## D-017 — Replay protection behind an atomic interface; recorded only after the signature verifies (S2, 2026-09-30)

- **Decision:** `ReplayGuard.checkAndRecord` atomically enforces per device+key: nonce uniqueness within a retention window and a strictly increasing `seq` (gaps allowed; reuse and rollback rejected). It is called only after HMAC verification, so unauthenticated traffic cannot burn nonces or advance sequences. `InMemoryReplayGuard` is local-only; a shared store can replace it in S9. Telemetry and heartbeat share one counter per device/key.
- **Reason:** Atomicity avoids check/record races; ordering prevents a denial-of-service on a legitimate device. Firmware must therefore persist its sequence (or seed it from trusted time) across reboots. This is HTTP request replay protection, distinct from observation dedupe.

## D-018 — Device registry holds no secrets; unknown health is not healthy (S2, 2026-09-30)

- **Decision:** `DeviceRegistry` (identity, org/facility/asset, status, active key ID, expected signals, firmware, last-seen, health) is separate from `DeviceKeyStore` (raw 32-byte keys), so Secret Manager can back the latter. Only `activeKeyId` is accepted. Health starts `UNKNOWN` and becomes concrete only through a heartbeat; `UNKNOWN` is treated as not healthy. The spec does not define a heartbeat payload, so S2 defines `{device_id, firmware_version, sent_at, health}`. The fixture device `DEV-SIM-001` and its key (the repeating pattern `0123456789abcdef` x4) are public, obviously synthetic, and grant nothing; no real ESP32 key exists in the repository.
- **Reason:** Principle 3 (missing data never becomes trusted) and secrets-out-of-Git.

## D-019 — S2 event flow and bus semantics (S2, 2026-09-30)

- **Decision:** `api` emits `telemetry.received` and `telemetry.authenticated` only for requests that passed authentication and schema validation (so unauthenticated traffic cannot flood the bus); `worker` emits `telemetry.normalized` then `telemetry.quality_assessed`, each caused by the previous event under one correlation ID. Payloads use camelCase; envelopes follow the spec (snake_case). `normalized` carries observations without quality; `quality_assessed` carries full `CanonicalObservation`s plus per-observation reason codes; duplicates are dropped (and counted) before either is emitted via `ObservationRepository.insertIfAbsent` on `device + signal + observedAt`. `EventBus` is `publish`/`subscribe` by event type; `InMemoryBus` delivers in order, queues events published from handlers, records history, and dead-letters handler failures. Event IDs come from an injectable `IdGenerator`. Time comes from the `clock` package.
- **Reason:** Keeps the flow deterministic and testable, and keeps a future `PubSubBus` drop-in. The domain packages from S1 still take explicit timestamps.

## D-020 — One shared edge-v1 mapping for hardware and simulator (S2, 2026-09-30)

- **Decision:** `normalization` owns `createEdgeV1Adapter`; `adapters/esp32` and `adapters/simulator` are thin instances differing only by adapter name and source type, so equivalent packets normalize identically (spec principle 16). Mapped fields: `temperature_c`→temperature (degC), `relative_humidity_pct`→relative_humidity (%), `vibration_rms_ms2`→vibration_rms (m/s2), `current_ma`→current (converted to A), `fan_a_load_pct`→load_percent (%), `chiller_b_running`→equipment_running. Unmapped fields, type mismatches and signals the device does not declare are reported as rejected readings, never silently dropped. `observed_at` is canonicalized to UTC ISO with milliseconds so equal instants share one dedupe identity. Known limitation: every reading is attributed to the device's single asset; separate assets for backup equipment (Fan B) need a later registry extension.
- **Reason:** Principle 16 and "no failure silently becomes success".

## D-021 — Plausibility thresholds in config; quality factors (S2, 2026-09-30)

- **Decision:** Physical plausibility ranges, staleness window and confidence factors live in `config/rules/data-quality.v1.json`, parsed and validated by `data-quality`; the file is loaded by the composition root, not by the package. Confidence is 1, halved when stale, halved when the device is not healthy, and 0 when out of range, observed in the future, or unauthenticated.
- **Reason:** Spec 50.10 (thresholds in versioned config). Deterministic, no baselines or statistics (S3).

## D-022 — Local runtime composition, `tsx`, and `pnpm dev` (S2, 2026-09-30)

- **Decision:** `scripts/local-runtime.ts` is the local composition root (the root package depends on the workspace packages it wires). `pnpm dev` (`scripts/dev.mjs`) starts api+worker as one process (they share the in-memory bus; separate Cloud Run deployables in S9) and the simulator as a separate process talking over HTTP. `web` is NOT started (Next.js arrives in S7); the launcher says so. `tsx` was added as a devDependency to run TypeScript sources (Node's type stripping cannot resolve our extensionless imports), and pnpm 12 required explicitly approving esbuild's install script (`allowBuilds` in `pnpm-workspace.yaml`). `pnpm smoke:s2` runs a real-HTTP smoke test against the runtime.
- **Reason:** Spec section 39 asks for `pnpm dev` to run web, api, worker and simulator; this is the honest S2 subset. The locked four-deployable architecture is unchanged.

## D-023 — Multi-asset device mapping is registry configuration (S3, 2026-09-30)

- **Decision:** A device record has a default `assetId` plus an optional `assetMapping { byField, bySignal }`. A reading's asset resolves `byField` (source field name) → `bySignal` (canonical signal) → default. The mapping travels in the `telemetry.authenticated` payload and `normalization` applies it; normalization contains no asset IDs. The synthetic device maps temperature/humidity to `AST-SIM-ZONE-1`, outdoor temperature to `AST-SIM-OUTDOOR`, `chiller_b_running` (backup capacity) to `AST-SIM-FAN-B`, and leaves vibration/current/load on the default `AST-SIM-FAN-A`. A one-asset device simply has no mapping. S2's `outdoor_temperature_c` source field was added to the shared edge-v1 mapping.
- **Reason:** One physical device observes several logical assets (spec section 28); creating fake devices to work around a one-asset model would corrupt device trust and identity. By-field precedence is needed when two source fields share a signal (e.g. two equipment-running flags).

## D-024 — Baseline model and statistics (S3, 2026-09-30)

- **Decision:** Identity is organization + facility + asset + signal + operating mode. Statuses: `LEARNING`, `READY`, `INSUFFICIENT_DATA`, `SUPERSEDED`. The warm-up window is measured in observation time from the first trusted sample (default 120 s, at least 12 samples; both in `config/rules/baselines.v1.json`), so tests advance simulated time and never wait. A window that ends with too few samples becomes `INSUFFICIENT_DATA`, which is terminal until an explicit re-baseline. `READY` baselines are frozen, so abnormal data cannot retrain them. Only trusted observations (authenticated, fresh, in range, healthy device, minimum confidence) are learned. Statistics are Welford count/mean/m2 with min/max (sample standard deviation); z-scores use `max(stddev, per-signal floor from config)` so near-constant baselines cannot explode. "Known normal" during warm-up is an operator assumption the system cannot verify. Re-baselining supersedes (never overwrites) the active baseline and starts version n+1; it needs an actor and reason, returns an audit record that the repository stores, and is never triggered automatically. No new event type is used for it; the audit package (later) will consume the record.
- **Reason:** Spec section 17 plus principle 3 (partial or untrusted data never becomes a trusted baseline).

## D-025 — Operating mode comes from load bands (S3, 2026-09-30)

- **Decision:** `vibration_rms` and `current` baselines are keyed by an operating mode derived from the same asset's `load_percent` at the same sample instant, using bands from config (`LOW_LOAD` below 50, `HIGH_LOAD` from 50). With no load observation the `DEFAULT` mode is used; if a load observation exists but is untrusted the mode is unknown and nothing is learned or evaluated. A mode without a READY baseline yields `INSUFFICIENT_DATA`; it is never judged against another mode's baseline.
- **Reason:** Spec 17 (compare current draw with the baseline for the current load where possible).

## D-026 — Detection: instants, persistence, severity (S3, 2026-09-30)

- **Decision:** A sample instant is one `observed_at` (a telemetry sample, spec section 33). Primary facts (vibration, current) must share the instant; context is outdoor temperature (trusted, within `contextMaxAgeSeconds`; threshold in degF, canonical value in degC) or a rising zone-temperature trend (least-squares slope over a trailing window; slopes under 1e-9 degC/h are treated as zero so floating-point noise never reads as "rising"). The compound rule needs vibration z >= 2 (inclusive) AND current deviation >= +8% (inclusive, positive only) AND (outdoor >= 105 F inclusive OR slope > 0 exclusive), all from `config/rules/cooling-electrical.v1.json`. Single abnormal signals, or both without satisfied context, are `WATCH`; missing, untrusted or baseline-less inputs are `INSUFFICIENT_DATA`, never `NORMAL`. Persistence counts distinct qualifying instants (3 required); a gap over 30 s restarts the count; `NORMAL`/`WATCH` instants reset it; `INSUFFICIENT_DATA` instants neither count nor reset. After the threshold, each further qualifying instant yields another `risk.detected` (same episode). Severity is `MODERATE` by default, `HIGH` when z >= 4 and deviation >= 15%, `CRITICAL` when HIGH and both context branches hold (all config).
- **Reason:** Spec 15.2 and 14. Context supports either branch, so S10 hardware stays viable if temperature responds slowly (spec 15.3). Control availability (backup equipment state) is recorded as a fact but not yet part of severity.

## D-027 — Case correlation and a state-neutral `RECORD_DETECTION` command (S3, 2026-09-30)

- **Decision:** An episode is identified by organization + facility + hazard type + primary asset (the primary asset is `assetIds[0]`). A matching case that is not `CLOSED` or `VERIFIED_IMPROVED` is "active": a new detection updates it (no duplicate case or event); otherwise a case (`OPEN`, origin `DETECTED_HAZARD`, `activeRiskEventId` set, baseline snapshot referenced) and a `DETECTED` risk event are created. To record the update, the S1 aggregate gained `RECORD_DETECTION`: it keeps the state, bumps `updatedAt`, may raise severity but never lower it, and is only legal in `OPEN`, `ACTION_REQUIRED` and `REOPENED` (later workflow states ignore it for now; the detection stays on the bus). This is the one S1-aggregate extension in S3. Recurrence after verified improvement is NOT handled: S5 must intercept a `VERIFIED_IMPROVED` match before this path creates a second case.
- **Reason:** Spec 4.1 (a case spans multiple detections); S4/S5 own the rest of the workflow.

## D-028 — S3 events and baseline snapshots (S3, 2026-09-30)

- **Decision:** `risk.observation_evaluated.v1` is emitted per rule-input observation (vibration, current, zone and outdoor temperature) at an instant that has a primary asset; its payload carries outcome (`NORMAL`/`WATCH`/`CANDIDATE_RISK`/`INSUFFICIENT_DATA`), the instant-level outcome, reason codes, rule id/version, baseline reference/status/mode, metrics and persistence progress, with no generated language. Evaluations are caused by `quality_assessed`; `risk.detected` by the first candidate evaluation of that instant; `case.created`/`case.updated` by `risk.detected`. Detections reference baselines by ID; a case references an immutable `BaselineSnapshot` (set of baseline IDs) created at case creation. Context observations at instants with no primary signals are recorded as facts but produce no evaluation event.
- **Reason:** Spec 14 pipeline; auditability of every conclusion without the event stream becoming a log of raw data.

## D-029 — Shared trust policy and S3 repositories (S3, 2026-09-30)

- **Decision:** `data-quality` owns `assessTrust`/`TrustPolicy` so baselines and detection gate on quality identically; the policy lives in the rule config (`requireHealthyDevice`, `minConfidence`). `repositories` gained only what S3 needs, all organization-scoped interfaces with in-memory implementations: baselines (history, snapshots, audit), detection state, cases (correlation lookup), risk events. `DetectionState` and the baseline/risk data types live in `contracts` so repository interfaces need no dependency on detection logic. No new third-party dependency was added.
- **Reason:** Clean dependency direction (repositories depend only on contracts) and Firestore-ready seams for S9.

## D-030 — Alert-delivery lifecycle rule (S4, 2026-10-01)

- **Decision:** The risk event becomes `ALERTED` only when the configured notification channel returns `SENT` for the `INITIAL` alert. Requesting or composing an alert changes nothing. A failed attempt keeps the event `DETECTED`, stores the failure (code, message, timestamps) on the alert, emits `notification.failed` and schedules a retry (`retryIntervalSeconds`, up to `maxDeliveryAttempts`, both in `config/escalation/`). After the last failed attempt the alert is `exhausted`; the escalation tick then escalates the still-`DETECTED` event so a human is reached. Alert IDs are deterministic (`ALR-<riskEventId>-<kind>`), so duplicate `case.created` processing creates no second alert. `SENT` means the local channel accepted the message (ConsoleEmail), never proof that a person read it. A sender that throws, or a role with no actor, is recorded as a failed attempt rather than an error.
- **Reason:** The brief forbids claiming delivery that did not happen; deterministic IDs make at-least-once event delivery safe.

## D-031 — Notification port and ConsoleEmail (S4, 2026-10-01)

- **Decision:** `NotificationSender` (channel + `send(request) -> NotificationResult`) lives in `packages/notifications`; `ConsoleEmail` is the only implementation and writes to an injectable sink (console by default). Recipients are actor IDs, never addresses, so a future `SmtpEmail` keeps addresses inside its adapter. Alert text is rule-based (a static phrase table over reason codes), contains no raw telemetry, no secrets and no action token, and states that a report is not proof of improvement. A `ScriptedNotificationSender` test double is exported from `@symbiosis/notifications/testing`.
- **Reason:** Spec section 39 (ConsoleEmail | SmtpEmail); forwardable action-link security is a later concern.

## D-032 — Local development identity and application authorization (S4, 2026-10-01)

- **Decision:** `packages/tenancy` holds `ActorContext` and a synthetic in-memory directory (e.g. `USR-FACILITY-MGR-001`, plus an actor in another organization for isolation tests); `packages/authz` maps roles to permissions. The HTTP layer identifies the caller with the `X-Demo-Actor-Id` header (or `?actor=` on the HTML pages), looks it up in the directory, and takes organization and facility scope from the directory, never from the request. Every service call scopes repository reads by `actor.organizationId` and checks facility access; another tenant's case is reported as `NOT_FOUND`, indistinguishable from a missing one. This is explicitly NOT authentication or production authorization; Firebase identity and real enforcement are S9/S11.
- **Reason:** S4 needs accountable actors without destroying the future tenant boundary (spec 36).

## D-033 — Escalation policy and the scheduler seam (S4, 2026-10-01)

- **Decision:** `config/escalation/escalation.v1.json` holds acknowledgement deadlines by severity (LOW 3600 s, MODERATE 900 s, HIGH 300 s, CRITICAL 120 s), retry interval and attempts, and the recipient roles (initial: FACILITY_MANAGER, escalation: ORG_ADMIN). `runEscalationTick` is a plain function over repositories and a `Clock`; the local runtime, tests, the `POST /api/v1/ops/tick` route (ORG_ADMIN only, local) and a future Cloud Scheduler call the same code. A tick retries due alerts first, then escalates. The deadline runs from when the initial alert was `SENT`, using the case's current severity. An acknowledged (or later) event is never escalated. Escalation changes operational urgency only; it never changes physical severity. The original alert is untouched; the escalation notification is a separate `ESCALATION` alert to the escalation role, and `risk.escalated` records the reason (`ACKNOWLEDGEMENT_OVERDUE` or `ALERT_DELIVERY_EXHAUSTED`).
- **S1 lifecycle adjustment:** `DETECTED -> ESCALATED` was added to the risk-event table, because an alert that can never be delivered otherwise leaves the event stuck with no path to a human. Regression tests pin the table (including that nothing new reaches a verification state).
- **Reason:** Spec 6 (no acknowledgement -> `ESCALATED`) and the failure-handling requirement.

## D-034 — Operations workflow rules (S4, 2026-10-01)

- **Decision:** `createOperations` (in `action-orchestration`) is the only entry point for acknowledge, assign, action-acknowledge, report and dismiss; HTTP routes only validate, call it and map errors (`NOT_FOUND` 404, `FORBIDDEN` 403, `INVALID_REQUEST` 400, `CONFLICT` 409). Rules: acknowledgement needs an `ALERTED` or `ESCALATED` event and does not touch the case or actions; assignment and reporting need `ACKNOWLEDGED` (or `ACTION_REPORTED` for further actions); assigning moves an `OPEN` case to `ACTION_REQUIRED` and sets the owner; reporting moves event and case to `ACTION_REPORTED` (from `OPEN` it first applies `REQUIRE_ACTION`), and a report without prior assignment creates the action for the reporter. Only the assignee can acknowledge an action. Duplicate acknowledgement and duplicate action reports are explicitly rejected (409), not silently idempotent. Each command computes every resulting state first and persists only if all succeed. A reported action is never a verification: there is no verification state, command, event or wording in S4, and `VERIFICATION PENDING` is a derived label shown while the case is `ACTION_REPORTED`. Actions come from `config/action-library/cooling-actions.v1.json` (stable `ACT-COOLING-*` IDs, a version, applicable hazard types); the parser rejects any entry with `controlsEquipment` other than `false` (RECOMMEND_ONLY). Attachments are reference IDs only. `MitigationAction` gained optional metadata (organization, assigner/time, library version, acknowledgement).
- **Reason:** Spec 7 and principle 2; keeps S1 invariants intact.

## D-035 — Detections during workflow states, audit, and dismissal (S4, 2026-10-01)

- **Decision:** `RECORD_DETECTION` is now also legal in `ACTION_REPORTED`: continued deterioration is recorded (state preserved, severity may only rise, a `DETECTION_RECORDED` audit entry, `case.updated` with `DETECTION_CONTINUED`) without resetting the case or creating a duplicate. `VERIFYING` and later states stay untouched until S5; the detection remains on the bus. The case view counts detections from the audit trail. A minimal append-only `AuditLog` (`packages/audit`, no hash chain yet) records case creation, detections, alert request/sent/failed, alerted, acknowledgement, assignment, action acknowledgement and report, escalation and dismissal. Dismissal (permissioned, requires a reason) moves the event to `DISMISSED_FALSE_ALARM` and closes the case administratively; the next qualifying detection would open a new case, so false-alarm suppression is an open design question for later phases.
- **Reason:** Closes the S3 known gap deterministically without inventing S5 behavior.

## D-036 — Minimal S4 case UI and event/contract changes (S4, 2026-10-01)

- **Decision:** The S4 "case UI" is two read-only, server-rendered HTML pages (`/ui/cases`, `/ui/cases/:id`) with no scripts, produced by the same `node:http` server and clearly labelled a workflow-proof surface; the Next.js workspaces, persona UIs and Trust Center remain S7. Sections follow spec 25 (what happened, accountability, what to do, what was done, did it work, evidence as audit references, sharing "Not available until S6"). Its text never contains the word "verified". `case.updated` was generalized with a `change` kind (`DETECTION_CONTINUED`, `ACTION_REQUIRED`, `ACTION_REPORTED`, `CASE_CLOSED`) and `previousState`. New events (all `.v1`): `risk.alert_requested`, `notification.requested|sent|failed`, `risk.alerted`, `risk.acknowledged`, `risk.escalated`, `risk.dismissed`, `action.assigned|acknowledged|reported`. New packages: `audit`, `tenancy`, `authz`, `escalation`, `notifications` (plus filled-in `action-orchestration`); no third-party dependency was added.
- **Reason:** Spec 14 pipeline and 24-25 information architecture, scoped to proving the human workflow.

## D-037 — Verification policy schema, fail-closed parsing (S5, 2026-10-01)

- **Decision:** `config/verification-policy/cooling-electrical.v1.json` (`schema: verification-policy.v1`, id `VPOL-COOLING-ELECTRICAL`, version `1`) holds everything the spec requires of a policy: reference/baseline behavior (`CASE_SNAPSHOT_THEN_ACTIVE_SAME_MODE`, pre-action lookback), post-action window (`settleSeconds`, `durationSeconds`), expected sample interval, `minObservations`, acceptable missingness (`maxMissingFraction`, `maxGapSeconds`), the sustained interval (`seconds`, `minObservations`), integrity (`requireAuthenticated`, `requiredDeviceHealth`, minimum observation confidence, `maxUntrustedFraction`), `minTelemetryConfidence`, the four criteria (vibration, current, backup capacity, zone temperature), `partial.enabled` and `recurrenceWatch.seconds`. `parseVerificationPolicy` validates every field and **throws** on anything malformed, partial or of another schema version; weakening authentication or device health, or making vibration/current non-required, is rejected. The engine contains none of the policy numbers (a test greps for them). The asset bindings for backup capacity (`AST-SIM-FAN-B`) and zone temperature (`AST-SIM-ZONE-1`) live in the policy because the prototype has no asset-topology model; a later phase may derive them.
- **Reason:** Spec 8.2 and 16: versioned JSON, never hard-coded thresholds; "no failure silently becomes success".

## D-038 — Verification window semantics and the tick-driven start (S5, 2026-10-01)

- **Decision:** The post-action window is `[latestReportedAt + settleSeconds, + durationSeconds]`, bounds inclusive, measured in observation time. Nothing is concluded before `now >= window.end` (the engine returns `complete: false`). `verification.started` is **not** emitted when `action.reported` arrives: the verification runner starts it on the scheduler seam (`runtime.tick()`, `POST /ops/tick`, `pnpm dev` interval) exactly like escalation (D-033), then evaluates attempts whose window has ended, in the same pass. This keeps the S4 smoke contract (a reported case stays `ACTION_REPORTED` with no `verification.*` event until the scheduler runs) and makes "start, wait, evaluate" explicit. Causation and correlation survive the gap: the `ACTION_REPORTED` audit entry now records the emitted `action.reported` event id (`details.emittedEventId`) and its correlation id, which the runner uses. A cycle covers the actions reported for the active event since the previous attempt; a verification belongs to exactly one case, event and cycle. Presentation stays `VERIFICATION PENDING` for both `ACTION_REPORTED` and `VERIFYING`. A second action cannot be reported while `VERIFYING` (409).
- **Reason:** Spec 14 sequence and the "no early success" rule, with deterministic tests under `ManualClock`.

## D-039 — Criterion semantics (S5, 2026-10-01)

- **Decision:** Every criterion is `PASS`, `FAIL` (trustworthy evidence does not meet the policy) or `INSUFFICIENT` (cannot be established); `passed === (outcome === "PASS")` and the validator rejects any mismatch. Evidence selection per observation: organization and facility equal the case's, asset and signal relevant to the criterion, observed inside the window, authenticated, fresh, in range, device healthy, confidence at least the policy minimum, device registered and ACTIVE and bound to the asset (`DEVICE_NOT_BOUND_TO_ASSET`), value type correct. **Vibration** and **current** use the operating mode of the same asset's load at the same instant (D-025) and the baseline of that exact mode, taken from the case baseline snapshot first and then the active READY baseline of the *same* mode; an observation whose mode is unknown or that has no such baseline is excluded (`OPERATING_MODE_UNKNOWN`, `NO_BASELINE_FOR_MODE:<mode>`), never judged against another mode. Metric: z-score (vibration) and signed percent deviation (current), as in detection. Over the trailing **sustained interval** (needs `sustained.minObservations` and no gap above `maxGapSeconds`, counting both edges): the share of samples at or below `targetMax` must be at least `passFraction` for PASS; otherwise FAIL, with reason `STILL_MATERIALLY_ABNORMAL` when more than `partialMaxAbnormalFraction` of samples are at or above `abnormalMin`, else `IMPROVED_BUT_NOT_AT_TARGET`. The band between `targetMax` and `abnormalMin` is the hysteresis/tolerance zone. **Backup capacity** is a required criterion only when a reported action of the cycle is listed in `requiredForActionLibraryIds`; it needs `equipment_running = true` observed for at least `passFraction` of the sustained interval (a report that backup was started is never evidence). **Zone temperature slope** has a configurable role (`SUPPORTING` by default): the least-squares slope over trusted samples must be at most `maxSlopeDegCPerHour` (needs `minSamples` over `minSpanSeconds`). **DATA_QUALITY** (required, never FAIL) checks per required series: trusted count, missingness against the expected sample count, gaps over the whole window, share of quality-excluded samples, mean confidence. **DEVICE_INTEGRITY** (required, never FAIL): zero tolerance for unauthenticated required-signal observations; every registered device bound to a required asset must be ACTIVE and `HEALTHY` in the registry at evaluation; the share of unhealthy or unbound data is capped.
- **Reason:** Spec 16 criteria, principle 3 (missing data never becomes trusted) and "do not use a different load/mode baseline merely because it exists".

## D-040 — Result precedence; PARTIAL vs INCONCLUSIVE vs NOT_IMPROVING (S5, 2026-10-01)

- **Decision:** In order: (1) `DEVICE_INTEGRITY` insufficient gives `INCONCLUSIVE` (an untrusted source proves nothing, including non-improvement); (2) a required physical criterion trustworthily `STILL_MATERIALLY_ABNORMAL`, required backup not observed running, or a required rising zone temperature gives `NOT_IMPROVING` (trusted evidence of non-improvement stands even when another signal is missing); (3) any other required criterion `INSUFFICIENT` gives `INCONCLUSIVE`; (4) required criteria that failed only as `IMPROVED_BUT_NOT_AT_TARGET` give `PARTIALLY_VERIFIED` if `partial.enabled`, else `NOT_IMPROVING`; (5) all required criteria `PASS` gives `VERIFIED`. `PARTIALLY_VERIFIED` therefore means "trustworthy data show material improvement into the tolerance band, but not at target": it is never a fallback for missing or untrusted data. As a backstop the engine validates every `VERIFIED` result with `validateVerificationAssessment` and downgrades a failure to `INCONCLUSIVE` (`ASSESSMENT_FAILED_VALIDATION`); tests assert the primary logic is right independently of the backstop (found by a mutation check). A processing error while evaluating becomes `INCONCLUSIVE` (`VERIFICATION_PROCESSING_FAILURE`); a malformed policy fails at startup; a coordinator or repository failure leaves the attempt `IN_PROGRESS` and is reported, never marked verified. The validator also rejects a criterion whose `passed` disagrees with its `outcome`.
- **Reason:** The brief's INCONCLUSIVE/NOT_IMPROVING distinction and "no failure silently becomes success".

## D-041 — Completeness and confidence calculation (S5, 2026-10-01)

- **Decision:** Per required series (vibration and current on the primary asset, the backup series when required, the zone series when required): `ratio = min(1, trustedSamples / expectedSamples)` with `expectedSamples = floor(windowSeconds / expectedIntervalSeconds) + 1`, and 0 when there is no trusted sample. `dataCompleteness` is the **minimum** ratio across those series, so a missing required signal gives 0 whatever the other signals look like. `telemetryConfidence` is the minimum across the same series of the mean confidence of trusted samples (0 when none). Assessment `confidence = dataCompleteness x telemetryConfidence` (4 decimals). These describe the evidence, not the truth of the conclusion: a solid NOT_IMPROVING with one missing signal reports low completeness.
- **Reason:** Spec: a high average confidence must not compensate for a missing required signal.

## D-042 — Evidence references (S5, 2026-10-01)

- **Decision:** A completed attempt stores typed `EvidenceReference`s (`OBSERVATION`, `BASELINE`, `ACTION`, `AUDIT`, `POLICY`, `DEVICE`) and the assessment lists their ids: every in-window observation considered for the relevant series (trusted ones and the excluded ones that explain an exclusion), the baselines actually used, the reported actions of the cycle, the `ACTION_REPORTED` and `VERIFICATION_STARTED` audit entries, `POLICY:<id>:<version>` and `DEVICE:<id>` registry facts. `resolveEvidence` (worker) proves each id names a real stored record and is asserted in the integration tests and the smoke. `DEVICE:<id>` points at the live registry record, so it is not a frozen snapshot; S6 will snapshot facts into immutable packages. No evidence package, manifest or hash exists in S5.
- **Reason:** Spec S5: evidence IDs yes, final evidence package no.

## D-043 — Recurrence matching, window and outside-window rule (S5, 2026-10-01)

- **Decision:** In the worker pipeline, *before* ordinary correlation, a `risk.detected` (the persistent compound rule, so a single WATCH signal can never qualify) is matched against `VERIFIED_IMPROVED` cases with the same organization, facility, hazard type and primary asset. The window ends at the verified attempt `recurrenceWatchEndsAt` (end of its post-action window plus the policy `recurrenceWatch.seconds`, fixed at completion, inclusive). Inside it: `recurrence.detected.v1`, then the same case moves to `REOPENED` with `recurrenceCount + 1`, a **new** `DETECTED` risk event becomes active (severity may only rise), the old event stays `VERIFIED`, prior attempts are untouched, and `case.reopened.v1` follows (the alerting consumer requests an INITIAL alert for the new event; audit `RECURRENCE_DETECTED` and `CASE_REOPENED`). The normal acknowledge, assign, report, verify cycle then continues on the same case. Outside the window (or when the case has no usable verified record) the detection opens a new case as in S3. A reopen failure throws (dead letter) rather than falling through to a duplicate. `RECORD_DETECTION` is now also legal in `VERIFYING`, `PARTIALLY_VERIFIED`, `NOT_IMPROVING` and `INCONCLUSIVE` (state preserved, severity may only rise), closing the S4 gap; `VERIFIED_IMPROVED` is intentionally excluded. Monitoring never stops: S3 evaluation is facility-wide and unaffected by case state.
- **Reason:** Spec 8.3 and the known S3/S4 recurrence gap; "do not keep merging risks forever".

## D-044 — Human follow-up after unsuccessful outcomes (S5, 2026-10-01)

- **Decision:** `assignAction` and `reportAction` accept an event in `PARTIALLY_VERIFIED`, `NOT_IMPROVING` or `INCONCLUSIVE` (besides `ACKNOWLEDGED` and `ACTION_REPORTED`); the case moves to `ACTION_REQUIRED` then `ACTION_REPORTED` using the unchanged S1 transition tables. These cases are never silently closed, and no new action generation exists (the approved library is used as is). Re-alerting on a failed cycle (demo stage 5) and a human "retry verification without a new action" command are not implemented.
- **Reason:** Spec: failed or partial verification stays available for human action.

## D-045 — Intervention prioritization (S5, 2026-10-01)

- **Decision:** `config/intervention-policy/risk-engineer-prioritization.v1.json` (`intervention-policy.v1`, `IPOL-RISK-ENGINEER-PRIORITIZATION` v1) is a set of rules over a closed list of trusted facts (severity, state, verification results and counts, consecutive unsuccessful verifications, recurrence count, escalation, data sufficiency, telemetry confidence, integrity issue, corroborating signals, insufficient remote evidence). Every matching rule contributes its reason code and the **highest** matching level wins, so rule order cannot change the outcome; with no match the default (`REMOTE_MONITORING`) applies. Shipped thresholds: recurred twice, three consecutive unsuccessful verifications, or CRITICAL unresolved with insufficient remote evidence give `SITE_VISIT_RECOMMENDED`; recurred once, two consecutive unsuccessful, two inconclusive, or CRITICAL not improving give `RISK_ENGINEER_REVIEW`; latest result not improving, partial or inconclusive, HIGH or CRITICAL unresolved, escalated acknowledgement, integrity issue or insufficient remote evidence give `REMOTE_REVIEW`; a confirmed improvement under watch gives `REMOTE_MONITORING`. Insufficient remote evidence is true for an unresolved case whose latest verification was inconclusive or whose data sufficiency is under `minimumForRemoteConfidence`. A recommendation is per case; a changed level or reason set supersedes the old one (kept as `SUPERSEDED`), an identical one writes nothing, and a closed case resolves it. Recalculation is event-driven: `case.created`, `risk.detected`, `case.updated` (detection continued or closed), `risk.escalated`, `verification.completed`, `recurrence.detected` and `case.reopened`; it emits `intervention.recommendation_updated.v1` and audit entries. Acknowledgement (permissions `INTERVENTION_READ` and `INTERVENTION_ACKNOWLEDGE`: admin and facility manager act, auditors read) changes only the recommendation. It schedules no one and touches no underwriting, premium or coverage. No `device.health_changed`, `telemetry.quality_changed` or `recommendation.overdue` event exists yet, so those spec triggers are not wired.
- **Reason:** Spec 23A.

## D-046 — New events, audit actions, API and earlier-test adjustments (S5, 2026-10-01)

- **Decision:** New events (all `.v1`): `verification.started`, `verification.completed`, `recurrence.detected`, `case.reopened`, `intervention.recommendation_updated`; `case.updated` gained changes `VERIFICATION_STARTED` and `VERIFICATION_COMPLETED`. New audit actions: `VERIFICATION_STARTED`, `VERIFICATION_COMPLETED`, `RECURRENCE_DETECTED`, `CASE_REOPENED`, `INTERVENTION_RECOMMENDED`, `INTERVENTION_ACKNOWLEDGED`, `INTERVENTION_RESOLVED`. API: `GET /api/v1/verifications/:id`, `GET /api/v1/interventions`, `GET /api/v1/interventions/:id`, `POST /api/v1/interventions/:id/acknowledge`; the case view gains `verification`, `verificationHistory`, `stayingFixed` and `intervention`, and the minimal page renders them. "Did it work?" shows a result label only when a completed persisted assessment agrees with the case state; otherwise it shows PENDING or "RESULT NOT AVAILABLE". ## D-047 — Evidence package creation policy (S6, 2026-10-01)

- **Decision:** An evidence package is created for **every completed verification** (`VERIFIED`, `PARTIALLY_VERIFIED`, `NOT_IMPROVING` and `INCONCLUSIVE` alike), so useful history is kept and the package says exactly what was concluded; a package never implies improvement, and nothing renames a result. None is created while a verification is pending. `startEvidenceBuilder` subscribes to `verification.completed.v1` and calls `EvidenceService.createForVerification`, which is idempotent per verification (a second call or a redelivered event returns the existing package and emits nothing). A failure is explicit: the builder returns a typed error (`UNRESOLVED_EVIDENCE`, `INCONSISTENT_SOURCE`, `SERIALIZATION_FAILURE`, `STORAGE_FAILURE`, ...), nothing is stored, linked or emitted, the subscription throws so the bus dead-letters it, and `runtime.tick()` retries through `createMissing()`. The service may write only: the object store, the package index, one audit entry, one event and the case's `latestEvidencePackageId` (a test greps the sources). It never touches verifications, risk events, baselines, actions or observations.
- **Reason:** Spec 19 and principle 10; the S6 brief ("the evidence builder cannot invent a fact").

## D-048 — Package structure, canonical serialization, SHA-256 manifest (S6, 2026-10-01)

- **Decision:** `evidence-package.v1` = `{packageId, schemaVersion, organizationId, facilityId, caseId, verificationId, createdAt, payload, artifacts, manifest, manifestSha256}`. The `payload` holds the spec-19 facts copied from trusted records (case identity, recommendation identity/source and approved actions, risk event, reported actions, acknowledgement, baseline and post-action windows, required and supporting criteria, data completeness and confidence, device/auth status, result, recurrence, policy/model versions, evidence reference descriptors, audit references, source label); it contains **no package id and no timestamp**, so identical source records always hash identically. `artifacts` are the referenced records themselves (observations, baselines, actions, audit entries, policy, device snapshot), each frozen as plain JSON with its own SHA-256. The `manifest` (`evidence-manifest.v1`) carries schema, hash algorithm, canonicalization id, package/org/facility/case/verification ids, `createdAt`, policy and builder versions, `payloadSha256`, and the sorted artifact descriptors (`id`, `kind`, `sha256`); `manifestSha256` is the hash of the canonical manifest. Canonical form `symbiosis-canonical-json.v1` is documented in `docs/EVIDENCE_STANDARD.md` (sorted keys, no whitespace, `undefined` properties omitted, shortest-round-trip numbers, plain JSON only, UTF-8). The only time in the package is the explicitly injected `createdAt` (from `Clock`); ids come from the injected `IdGenerator`, so two identical runs produce byte-identical packages (tested). `verifyEvidencePackage` recomputes every artifact hash, the payload hash, the manifest hash, the descriptor lists and the identity fields from the package alone and never throws. `EvidenceService.load` additionally requires the stored bytes to be the canonical form and to match the index record (a self-consistent forgery is therefore still caught). Not a blockchain: hash-based evidence is sufficient for the prototype (spec 37).
- **Storage:** `EvidenceObjectStore` (`putIfAbsent`/`get`, in `evidence`) holds the canonical bytes under `evidence/<org>/<id>.json`; `EvidencePackageRepository` (in `repositories`) indexes metadata, one package per verification. Neither interface can overwrite or delete, so a package is immutable and history stays accessible; later activity creates a new package. Only in-memory implementations exist (the Cloud Storage adapter is S9; no cloud SDK was added).
- **Reason:** Spec 19, 39 and the S6 brief.

## D-049 — Snapshot semantics (S5 `DEVICE:<id>` fix) (S6, 2026-10-01)

- **Decision:** The verification runner now stores a frozen copy of the device facts it gave the engine (`VerificationAttempt.deviceSnapshots`: id, status, health, assets, firmware, last seen, capture time; no key material) on the completed attempt. `DEVICE:<id>` evidence references resolve to that copy, both in the evidence package and in the S5 `resolveEvidence` (the live registry is only a fallback for attempts that predate snapshots), so a later heartbeat, key change or disablement cannot rewrite history, and the package describes the devices **as known at verification time**. Every other mutable record cited by a package (case, risk event, actions, baselines whose status can change, policy) is embedded as a hashed snapshot at creation and never re-read, so later changes (including a recurrence reopening the case) leave existing packages untouched. The audit references are bounded to the entries up to the verification's own completion entry. An attempt without a snapshot cannot yield a package that cites a device (explicit failure).
- **Reason:** The S5 known issue and the S6 brief ("package must represent what was known at verification time").

## D-050 — Consent scope vocabulary and raw telemetry (S6, 2026-10-01)

- **Decision:** Scopes: `RECOMMENDATION`, `EVENT_SUMMARY`, `ACTION_SUMMARY`, `BEFORE_AFTER_METRICS`, `VERIFICATION_RESULT`, `VERIFICATION_CONFIDENCE`, `RECURRENCE_STATUS`, `EVIDENCE_ARTIFACTS` (the spec 20.2 categories), plus `INTERVENTION_RECOMMENDATION` (added: the prioritization output reveals verification and recurrence facts, so it needs its own consent) and `RAW_TELEMETRY`. `EVIDENCE_CONSENT_SCOPES` (the broad grant, used as the UI default) excludes `RAW_TELEMETRY`; no other scope implies it. Granting it needs the separate permission `SHARING_GRANT_RAW_TELEMETRY` (ORG_ADMIN only, not FACILITY_MANAGER). Raw observations are released only by an explicit request (`GET /insurance/v1/cases/:id/evidence?include=raw_telemetry`, no new route) when the active agreements include the scope; asking without the scope is an audited **denial**, not a silent omission, and holding the scope without asking releases nothing extra. The only code that lists observation values is `projectRawTelemetry`, called from that one branch (tests assert this).
- **Reason:** Spec 20 ("raw telemetry is a separate, explicit scope and is off by default") and the S6 brief.

## D-051 — Authorization behavior (S6, 2026-10-01)

- **Decision:** `SharingAgreement` follows the spec (`agreementId`, `organizationId`, `recipientOrganizationId`, `scopes`, `facilityIds`, `effectiveFrom`, optional `expiresAt`/`revokedAt`, `createdBy`) plus `createdAt`, `revokedBy`, `revocationReason`. Creation derives the granting organization and creator from the authenticated actor (request-supplied organization ids are ignored) and validates: permission `SHARING_MANAGE`; recipient is a known organization of type `INSURER` or `BROKER` and differs from the grantor; scopes known and non-empty (duplicates collapsed); facilities belong to the grantor's organization (server-side directory) and are reachable by the actor; `effectiveFrom`/`expiresAt` are valid ISO times, `expiresAt` after `effectiveFrom` and in the future. Every insurer read re-evaluates `evaluateAccess` (pure, deny-by-default) over the recipient's stored agreements at the current time: recipient organization (taken from the actor, never the request), owner, facility coverage, active window `[effectiveFrom, expiresAt)`, revocation (any `revokedAt` means revoked, effective at once, even at the same instant), and scope; scopes are the union of the active agreements covering the facility. Denial reasons exposed: `NO_AGREEMENT_FOR_TARGET`, `AGREEMENT_REVOKED`, `AGREEMENT_EXPIRED`, `AGREEMENT_NOT_YET_EFFECTIVE`, `SCOPE_NOT_GRANTED`; a case that does not exist, belongs to another tenant or sits in an uncovered facility all answer `NO_AGREEMENT_FOR_TARGET`, so existence is never revealed (403 `ACCESS_DENIED`; insured-side or unknown roles get 403 `FORBIDDEN`/401). Order per read: authorize, load and verify the package (a failing package is withheld: 500 `INTEGRITY_FAILURE`), project, **audit**, release; if the audit write fails nothing is released (`AUDIT_FAILURE`); a denial stands even if its own audit write fails. Revocation (`POST /api/v1/sharing-agreements/:id/revoke`, permission and facility access in the owning organization only, 409 when repeated) keeps the agreement and its terms, sets the revocation fields once, takes effect for the next read, and never touches packages or earlier audit entries. A package created before an agreement's `effectiveFrom` is releasable once the agreement is active (the window governs access time, not package age).
- **Reason:** Spec 20 and 36; S6 brief ("every insurer read validates ...", "no failure becomes authorization success").

## D-052 — Sharing-state transitions (S6, 2026-10-01)

- **Decision:** `case.sharingState` is derived from facts (`deriveSharingState`): `NOT_SHARED` (no package), `SHAREABLE` (a package exists, nothing ever shared), `SHARED` (an active agreement covering the facility releases package content, i.e. has at least one package-bearing scope; `RECOMMENDATION`/`INTERVENTION_RECOMMENDATION` alone do not), `REVOKED` (it was shared and no active agreement remains, whether revoked **or expired**, which the four-value vocabulary cannot distinguish). A package alone never produces `SHARED`. Reconciliation points: `evidence.package_created` (-> `SHAREABLE`, then any active agreement releases it), agreement creation, agreement revocation, and the scheduler tick (`reconcileAll`, which catches expiry and not-yet-effective agreements that have started). A release writes a `SharedEvidenceRecord` (unique per agreement and package) and emits `evidence.shared.v1` once. The case is changed only through the new documentation commands in `risk-cases` (`RECORD_EVIDENCE_PACKAGE`, `SET_SHARING_STATE`): they are **not** lifecycle transitions and preserve state, severity, verification references and `updatedAt` (which the recurrence-watch display reads). A new package becomes `latestEvidencePackageId` unless a newer verification already has one. Invariant added: any sharing state other than `NOT_SHARED` requires `latestEvidencePackageId`.
- **Reason:** "Evidence creation is documentation, not risk-state mutation" and "do not mark SHARED merely because a package exists".

## D-053 — Insurer DTOs and the six locked routes (S6, 2026-10-01)

- **Decision:** `GET /insurance/v1/sites`, `/sites/:id/cases`, `/cases/:id`, `/cases/:id/evidence`, `/recommendations`, `/interventions` return purpose-built, scope-filtered DTOs, never the internal objects. There is no insurer sensor dashboard and no write route. Probes that reach no data are audited under the requester's organization; attempts that reach an owner's data are audited under the owner's organization (so the insured can see them).
- **Reason:** Spec 20, 43 and the S6 brief.
